Tasks need more than source code. They also need the right Node.js, package manager, and language toolchain versions, plus your dependencies. With managed toolchains, your repository declares those versions in the files it already uses, [`turbo setup`](/docs/reference/setup) installs exactly those versions inside the repository, and [`turbo run`](/docs/reference/run) uses them for every task.

A new contributor or CI job only needs the [standalone `turbo` binary](/docs/getting-started/installation#global-installation). It doesn't need Node.js, a package manager, rustup, uv, or Go installed first.

```bash title="Terminal"
turbo setup
turbo run build
```

## How it works

1. Your repository declares versions in native files, such as `.nvmrc` and the `packageManager` field of `package.json`.
2. `turbo setup` resolves each declaration to an exact release, records it in `turbo.lock`, downloads and verifies that release, and installs it into `.turbo/tools`.
3. `turbo setup` installs your dependencies with each package manager's frozen install, such as `pnpm install --frozen-lockfile`, from your committed lockfiles.
4. You commit `turbo.lock`. Every contributor and CI job then gets the same versions.
5. `turbo run` puts the installed tools first on `PATH` for every task. [`turbo exec`](/docs/reference/exec) and the [shell hook](/docs/reference/hook) do the same for commands outside of tasks.

`turbo setup` never runs tasks. It prepares tools and dependencies, then exits.

## What `turbo setup` manages

| Toolchain                                            | Tools                          | Declared in                                       | Dependencies                                              |
| ---------------------------------------------------- | ------------------------------ | ------------------------------------------------- | --------------------------------------------------------- |
| JavaScript                                           | Node.js, npm, pnpm, Yarn, Bun  | `.nvmrc`, `.node-version`, and `package.json`     | `npm ci`, `pnpm install`, `yarn install`, `bun install`   |
| [Rust](/docs/reference/setup#rust) (experimental)    | rustup and the Rust toolchain  | `rust-toolchain.toml`                             | `cargo fetch --locked`                                    |
| [Python](/docs/reference/setup#python) (experimental) | uv and CPython                | `uv.toml`, `pyproject.toml`, and `.python-version` | `uv sync --locked --all-packages`                        |
| [Go](/docs/reference/setup#go) (experimental)        | Go                             | `go.work` or `go.mod`                             | `go mod download`                                         |
| [Additional tools](/docs/reference/additional-tools) | Any CLI you pin, like `protoc` | `setup.additionalTools` in `turbo.json`           | None                                                      |

Rust, Python, and Go follow Turborepo's [experimental support for those languages](/docs/guides/multi-language), so they need their workspace Future Flags. See [Supported declarations](/docs/reference/setup#supported-declarations) for every file `turbo setup` reads.

## Getting started

<Steps>
<Step>
### Install `turbo` globally

Install the standalone `turbo` binary. It doesn't need Node.js or a package manager. See [Global installation](/docs/getting-started/installation#global-installation).

</Step>
<Step>
### Ignore `.turbo/` in Git

Installed tools live in `.turbo/tools`, which must be ignored and untracked. `turbo setup` refuses to install tools otherwise. Outside a Git repository, such as in [pruned output](#pruning), it skips this check.

```txt title="./.gitignore"
/.turbo/
```

</Step>
<Step>
### Declare your versions

Declare Node.js and your package manager at the root of your repository:

```txt title="./.nvmrc"
24
```

```json title="./package.json"
{
  "packageManager": "pnpm@10.18.0"
}
```

`turbo setup` installs your dependencies by default, so it also needs your package manager's committed lockfile, such as `pnpm-lock.yaml`. If your repository doesn't have one yet, run `turbo setup --tools-only`, then create it with the managed package manager: `turbo exec -- pnpm install`.

</Step>
<Step>
### Run `turbo setup`

```bash title="Terminal"
turbo setup
```

The first run creates `turbo.lock`, installs the tools, and then installs your dependencies:

```txt title="Terminal"
javascript: tools managed (inferred); dependencies locked (inferred)
turbo.lock created. Commit turbo.lock to share the exact managed tool selections.
node: locked 24.21.0
pnpm: locked 10.18.0
node 24.21.0: installed
pnpm 10.18.0: installed
Managed tools use 218.9 MB in this clone's .turbo/tools.
Shared download cache: 62.3 MB.
Installing javascript dependencies from pnpm-lock.yaml with managed pnpm 10.18.0: pnpm install --frozen-lockfile (dependency installation, not a Turborepo task)
pnpm 10.18.0: native pnpm policy; project scripts run; dependency scripts run only for allowed packages
Permitted lifecycle scripts run package code that can start other commands. turbo setup runs no Turborepo tasks.
...
javascript dependencies: installed; pnpm-lock.yaml unchanged
Dependencies: javascript installed. No Turborepo tasks run.
```

The first line is the effective [setup policy](/docs/reference/setup-policy#output) for each toolchain. Verified downloads also go into a [shared download cache](#disk-use-and-cleanup) in your user cache directory, so other clones reuse them without downloading again.

</Step>
<Step>
### Commit `turbo.lock`

Committing `turbo.lock` makes the repository managed for everyone. From then on, `turbo run` requires `turbo setup` on every machine and in every CI job. See [How `turbo run` uses managed tools](#how-turbo-run-uses-managed-tools).

</Step>
<Step>
### Run tasks

```bash title="Terminal"
turbo run build
```

Tasks use the managed Node.js and pnpm, even when other versions are installed on your machine.

</Step>
</Steps>

## `turbo.lock`

`turbo.lock` is a small, committed JSON file that records the toolchain each declaration resolved to. For each tool, it contains:

- The exact version.
- The declarations it came from, such as `.nvmrc` or `package.json#/packageManager`.
- The verified download for each platform: its URL, SHA-256 digest, archive layout, and the executables it provides.

This excerpt shows one platform:

```jsonc title="./turbo.lock"
{
  "schemaVersion": 0,
  "tools": {
    "node": {
      "adapter": "node",
      "version": "24.21.0",
      "declarations": [
        {
          "file": ".nvmrc",
          "request": "24"
        }
      ],
      "options": {
        "bundled-npm": ["11.19.0"]
      },
      "installation": {
        "kind": "managed",
        "artifacts": {
          "linux-x64-gnu": {
            "distribution": {
              "url": "https://nodejs.org/dist/v24.21.0/node-v24.21.0-linux-x64.tar.gz",
              "sha256": "6e1db87ef58b8819e5d5402eff1536491b18edd8eb7bee5ef7897876e88dc5ff",
              "format": "tar-gz",
              "rootPrefix": "node-v24.21.0-linux-x64",
              "executables": {
                "node": "bin/node",
                "npm": "bin/npm",
                "npx": "bin/npx"
              }
            }
          }
          // ...other platforms
        }
      }
    },
    "pnpm": {
      // ...
    }
  }
}
```

`turbo.lock` isn't a dependency lockfile. It doesn't replace `pnpm-lock.yaml`, `Cargo.lock`, or `uv.lock`, and it never contains your dependency graph. It never contains credentials either.

Don't edit `turbo.lock` by hand. Change your declarations and run `turbo setup` instead.

### Portability

`turbo.lock` records downloads for every platform its tools publish, so a lock created on macOS works unchanged on Linux and Windows. [Frozen](/docs/reference/setup#frozen-mode) setup never adds a platform to it. The installed tools in `.turbo/tools` belong to one clone and are never committed.

### When `turbo.lock` changes

`turbo setup` keeps existing selections unless you change a declaration or ask for an update:

| Situation                                               | Local `turbo setup`                                        | Frozen or CI `turbo setup` |
| ------------------------------------------------------- | ---------------------------------------------------------- | -------------------------- |
| No `turbo.lock`                                         | Creates it                                                 | Fails                      |
| A declaration changed or was removed                    | Re-resolves only that tool, updates the lock, prints diff  | Fails and names it         |
| A newer release matches an unchanged request, like `24` | Keeps the locked version                                   | Keeps the locked version   |
| [`--update-lock`](/docs/reference/setup#--update-lock)  | Re-resolves every request to the newest match              | Requires `--no-frozen`     |
| [`--force`](/docs/reference/setup#--force)              | Reinstalls the locked versions and never changes the lock  | Same                       |

When `turbo setup` updates the lock, it prints each change:

```txt title="Terminal"
turbo.lock updated. Commit turbo.lock to share the exact managed tool selections.
node: 24.21.0 -> 22.23.3
```

To keep `turbo.lock` current when Renovate or Dependabot change a declaration, see [Updating turbo.lock with dependency bots](/docs/guides/updating-turbo-lock).

### Change detection

In a managed repository, `turbo.lock` is a global dependency for [`--affected`](/docs/reference/run#--affected), Git range [filters](/docs/reference/run#--filter-string), and [`turbo query`](/docs/reference/query). Changing it marks every package as changed.

### Pruning

In a managed repository, [`turbo prune`](/docs/reference/prune) copies `turbo.lock`, the declaration files it records, and the root `turbo.json` into the output. With `--docker`, both `json/` and `full/` receive them. The pruned output can run `turbo setup` without a Git repository. To build pruned output in Docker, see [Docker](/docs/guides/tools/docker#managed-toolchains).

## How `turbo run` uses managed tools

A repository is managed when its root contains `turbo.lock`. Without one, `turbo run` behaves exactly as before.

In a managed repository, every `turbo run`:

1. **Validates setup first.** Before it builds the graph, `turbo run` checks that the tools in `.turbo/tools` match `turbo.lock` and your declarations, are intact, and were installed by `turbo setup` for your user in this clone. If anything is wrong, it fails and tells you to run `turbo setup`. It never downloads tools, and it never falls back to tools on your `PATH`.
2. **Activates the tools.** The managed tools come first on `PATH`, together with the variables they need, such as `CARGO_HOME` for Rust or `GOROOT` for Go. `turbo`'s own probes, such as `cargo metadata` and Go workspace discovery, use them too. For tasks, this applies after [environment mode](/docs/crafting-your-repository/using-environment-variables#environment-modes) filtering, in both strict and loose mode.
3. **Hashes the toolchain.** Task hashes include the selected toolchain. See [Caching](#caching).

`turbo run` checks the installation again before each task starts. If the tools changed during the run, the task fails instead of starting.

### Caching

Managed task hashes include an identity of the selected toolchain. It combines the locked downloads for the current platform with host details: operating system, architecture, C library family and version on Linux, kernel release, and CPU features. Installation paths aren't included, so moving a clone doesn't cause cache misses.

As a result, changing a locked tool invalidates task caches, and [Remote Cache](/docs/core-concepts/remote-caching) hits require machines with matching host details. In [run summaries](/docs/reference/run#--summarize), the identity appears in the global hash's `rootKey`.

### Repository-local `turbo`

When you run the global `turbo` in a repository that installs `turbo` as a dependency, it normally [hands off to the local version](/docs/getting-started/installation#repository-installation). In a managed repository, it first asks the local `turbo` whether it supports the repository's `turbo.lock`. If it doesn't, the run fails with upgrade guidance:

```txt title="Terminal"
repository-local CLI at <path> cannot provide the required managed-run capability for turbo.lock schema 0
```

`turbo` never replaces the repository's version with the global one, and it never downloads one. Upgrade the repository's `turbo`, or remove it from your dependencies and use the global binary.

<Callout type="warn">
  Handing off to a repository-local `turbo` in a managed repository works only
  on macOS on Apple silicon today. On other platforms, a repository-local
  `turbo` fails this check. Use the global `turbo` binary in managed
  repositories. See [Managed toolchain
  platforms](/docs/reference/managed-toolchain-platforms#repository-local-turbo).
</Callout>

A repository-local `turbo` that you start directly, such as with `pnpm turbo` or `npx turbo`, skips the global binary. Versions without managed toolchain support don't read `turbo.lock`, so their tasks use the tools on your `PATH`.

## Using managed tools outside of tasks

`turbo run` activates the managed tools only for the tasks it starts. For everything else, use one of these:

- **The [shell hook](/docs/reference/hook)** puts the managed tools first on `PATH` while your bash, zsh, fish, or PowerShell session is inside the repository, and restores `PATH` when you leave. The standalone installers add it by default.
- **[`turbo exec -- <command>`](/docs/reference/exec)** runs one command with the managed tools. Use it in scripts, CI steps, `cmd.exe`, and processes started by other applications. See [when to use `turbo exec`](/docs/reference/hook#when-to-use-turbo-exec).

When `turbo.lock` changes after `turbo setup`, for example after `git pull`, the shell hook keeps the previously installed tools active and asks you to run `turbo setup`. `turbo run` and `turbo exec` fail until you do.

## Using `turbo setup` in CI

Install the standalone `turbo` binary in your CI job, as described in [Global `turbo` in CI](/docs/crafting-your-repository/constructing-ci#global-turbo-in-ci), then run `turbo setup` before your tasks:

```yaml title=".github/workflows/ci.yml"
steps:
  - uses: actions/checkout@v4
  - run: curl -fsSL https://turborepo.dev/install | sh
  - run: turbo setup
  - run: turbo run build test
```

When `turbo` detects CI, `turbo setup` uses [frozen mode](/docs/reference/setup#frozen-mode) by default. It installs exactly what `turbo.lock` records and fails without writing if `turbo.lock` is missing or no longer matches your declarations:

```txt title="Terminal"
  x turbo.lock declarations changed: node: .nvmrc
  help: Run `turbo setup --tools-only` locally and commit the updated
        turbo.lock, then retry CI.
```

To check an existing installation without changing anything, use [`turbo setup --check`](/docs/reference/setup#--check). To speed up repeated jobs, cache the [shared download cache](#disk-use-and-cleanup) and your package manager's store between runs.

## Disk use and cleanup

Each clone and worktree has its own `.turbo/tools`. Verified downloads are also kept in a shared download cache that every clone on the machine reuses, so a second clone installs without downloading. The shared cache is in `turborepo/setup-artifacts` inside your user cache directory:

| Platform | Shared download cache                                |
| -------- | ---------------------------------------------------- |
| macOS    | `~/Library/Caches/turborepo/setup-artifacts`         |
| Linux    | `$XDG_CACHE_HOME/turborepo/setup-artifacts`, or `~/.cache/turborepo/setup-artifacts` |
| Windows  | `%LOCALAPPDATA%\turborepo\setup-artifacts`           |

Nothing in the shared cache is ever put on `PATH`. Tools are always installed into a clone's `.turbo/tools` first, and verified again on the way.

`turbo setup` cleans up automatically and reports disk use at the end of each run:

```txt title="Terminal"
Managed tools use 218.9 MB in this clone's .turbo/tools.
Keeping 218.9 MB of replaced managed tools for 7 days after replacement in case a running task still uses them.
Shared download cache: 129.6 MB.
```

- **Replaced installations** that `turbo.lock` no longer selects are kept for 7 days after they're replaced, in case a running task still uses them, then removed by the next `turbo setup`.
- **Shared downloads** that no `turbo setup` on the machine used for 90 days are removed.

To remove everything yourself, delete `.turbo/tools` in each clone and the shared download cache directory.

## Upgrading from the experimental release

Before this release, managed toolchains required `futureFlags.experimentalSetup` in `turbo.json`. That flag has been removed, and setting it is now an error. Remove it from your root `turbo.json` or `turbo.jsonc`. A root `turbo.lock` is all a repository needs.

## Limitations

- **Experimental languages.** Rust, Python, and Go setup need `experimentalCargoWorkspaces`, `experimentalPythonWorkspaces`, and `experimentalGoWorkspaces`, like the rest of Turborepo's support for those languages. See [Supported declarations](/docs/reference/setup#supported-declarations).
- **Exact package manager versions.** npm, pnpm, Yarn, and Bun must be pinned to an exact version. Node.js, Rust, Python, uv, and Go can use ranges and channels.
- **Platforms.** See [Managed toolchain platforms](/docs/reference/managed-toolchain-platforms) for what's supported on each operating system, including musl-based Linux distributions, such as Alpine, which can only use [`verify-system`](/docs/reference/setup-policy#verify-system).
- **Repository-local `turbo`.** See [Repository-local `turbo`](#repository-local-turbo).
- **`turbo watch`.** In a managed repository, [`turbo watch`](/docs/reference/watch) doesn't run tasks. Use `turbo run`.
- **One `turbo setup` per Docker `RUN` instruction.** Each `RUN` instruction that uses the managed tools must run `turbo setup` first. See [Docker](/docs/guides/tools/docker#managed-toolchains).
- **Unauthenticated sources.** Tools download from their official sites or from [mirrors](/docs/reference/setup-policy#mirrors) that don't need credentials. Mirrors that require authentication aren't supported.
