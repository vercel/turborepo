The root `setup` key in `turbo.json` or `turbo.jsonc` sets repository-wide defaults for the experimental `turbo setup` command. Without it, `turbo setup` infers what to prepare from your declaration files, such as `.nvmrc` and the `packageManager` field of `package.json`. Most repositories don't need a `setup` key.

```jsonc title="./turbo.json"
{
  "$schema": "https://turborepo.dev/schema.json",
  "futureFlags": {
    "experimentalSetup": true,
  },
  "setup": {
    "dependencies": "skip",
  },
}
```

<Callout type="warn">
  The `setup` key is experimental and can change in any release. In this
  release, `turbo setup` installs dependencies only with the package managers
  listed in [Dependencies](/docs/reference/setup#dependencies). It reports
  dependencies for other package managers and toolchains as skipped.
</Callout>

## Requirements

- The `setup` key requires `futureFlags.experimentalSetup` to be `true` in the same file. Without the flag, every command that reads the root configuration, including `turbo run`, `turbo setup`, and `turbo prune`, exits with an error.
- `setup` is only allowed in the root `turbo.json` or `turbo.jsonc`. It's an error in a [Package Configuration](/docs/reference/package-configurations).
- The `rust`, `python`, and `go` keys also require `futureFlags.experimentalCargoWorkspaces`, `experimentalPythonWorkspaces`, and `experimentalGoWorkspaces`.
- Unknown keys and values are errors.

## Options

| Key                | Values                                   | Default     |
| ------------------ | ---------------------------------------- | ----------- |
| `tools`            | `"managed"`, `"verify-system"`, `"skip"` | `"managed"` |
| `dependencies`     | `"locked"`, `"skip"`                     | `"locked"`  |
| `lifecycleScripts` | `"native"`, `"skip"`                     | `"native"`  |

Set these keys at the top of `setup` to apply them to every toolchain, or inside a toolchain key to apply them to one toolchain. The toolchain keys are `javascript`, `rust`, `python`, and `go`. Each accepts the same three keys.

```jsonc title="./turbo.json"
{
  "futureFlags": {
    "experimentalSetup": true,
    "experimentalCargoWorkspaces": true,
  },
  "setup": {
    "dependencies": "skip",
    "rust": { "tools": "skip" },
  },
}
```

### `tools`

How `turbo setup` prepares a toolchain's tools:

- `managed`: Download, verify, and install the version recorded in `turbo.lock` into `.turbo/tools`. This is the default.
- `verify-system`: Use a tool that's already installed after verifying that it matches `turbo.lock`. See [`verify-system`](#verify-system).
- `skip`: Neither install nor verify the toolchain. Tasks use whatever is on `PATH`. A skipped toolchain also skips its dependencies.

### `dependencies`

How `turbo setup` prepares a toolchain's dependencies:

- `locked`: Install dependencies from the committed lockfile without changing it. This is the default.
- `skip`: Don't install dependencies.

With `locked`, a missing lockfile is an error, and `turbo setup` never creates or rewrites one. See [Dependencies](/docs/reference/setup#dependencies) for the commands it runs.

`"dependencies": "locked"` can't be combined with `"tools": "skip"` for the same toolchain, because dependency installation needs a managed or verified tool.

### `lifecycleScripts`

Whether package managers may run dependency lifecycle scripts, such as `postinstall`, when `turbo setup` installs dependencies:

- `native`: Keep each package manager's own defaults and the settings committed to your repository, such as allowlists of packages that may run build scripts. `turbo setup` never enables scripts that the package manager or your repository blocks. This is the default.
- `skip`: Pass the package manager's own flag for skipping scripts. If a package manager has no such flag, setup fails instead of claiming the scripts were skipped.

`turbo setup` prints the effective policy before each install. `skip`, and the [`--ignore-scripts`](#cli-overrides) flag, map to these flags:

| Package manager           | Flag passed                       |
| ------------------------- | --------------------------------- |
| npm, pnpm, Yarn 1, or Bun | `--ignore-scripts`                |
| Yarn 3 and later          | `--mode=skip-build`               |
| Yarn 2                    | None. Setup fails.                |
| uv                        | `--no-build`                      |
| Cargo and Go              | None needed. They run no scripts. |

With uv, `--no-build` refuses source builds, so packages without a compatible wheel fail to install.

Lifecycle scripts are package code that can start other commands. They aren't Turborepo tasks: `turbo setup` never runs tasks.

## Precedence

For each toolchain, `turbo setup` uses the first value it finds:

1. A `turbo setup` flag for this invocation.
2. The toolchain's key, such as `setup.javascript.tools`.
3. The top-level key, such as `setup.tools`.
4. The default.

If a toolchain's `tools` resolves to `skip`, its `dependencies` are skipped too.

### CLI overrides

Flags override repository policy for one invocation without changing `turbo.json`:

| Flag               | Overrides                                           |
| ------------------ | --------------------------------------------------- |
| `--tools-only`     | `dependencies`, which becomes `skip` everywhere     |
| `--ignore-scripts` | `lifecycleScripts`, which becomes `skip` everywhere |

No flag overrides `tools`. No policy key sets frozen or offline mode. Those come from `turbo setup` flags, and frozen mode is also the default in CI.

### Example

```jsonc title="./turbo.json"
{
  "futureFlags": {
    "experimentalSetup": true,
    "experimentalCargoWorkspaces": true,
  },
  "setup": {
    "tools": "managed",
    "dependencies": "skip",
    "javascript": { "tools": "verify-system" },
    "rust": { "tools": "skip" },
  },
}
```

| Toolchain    | Tools           | Dependencies                          |
| ------------ | --------------- | ------------------------------------- |
| `javascript` | `verify-system` | `skip`, from `setup.dependencies`     |
| `rust`       | `skip`          | `skip`, because its tools are skipped |

## Output

Before downloading or verifying anything, `turbo setup` prints one line per toolchain with the effective values and where each came from: `inferred`, `turbo.json setup policy`, or a flag.

```txt title="Terminal"
javascript: tools managed (inferred); dependencies skipped (turbo.json setup policy)
rust: skipped (turbo.json setup policy); turbo setup neither provisions nor verifies its tools, so tasks use whatever is on PATH
```

A line appears for `rust`, `python`, or `go` only when its workspace flag is enabled.

## Tools-only repositories

Set `"dependencies": "skip"` to make tools-only setup the repository default. [`turbo setup --plan`](/docs/reference/setup#--plan) and [`turbo setup --check`](/docs/reference/setup#--check) then work without `--tools-only`, locally and in CI:

```jsonc title="./turbo.json"
{
  "futureFlags": {
    "experimentalSetup": true,
  },
  "setup": {
    "dependencies": "skip",
  },
}
```

```bash title="Terminal"
turbo setup
```

```txt title="Terminal"
javascript: tools managed (inferred); dependencies skipped (turbo.json setup policy)
turbo.lock created. Commit turbo.lock to share the exact managed tool selections.
node: locked 24.21.0
pnpm: locked 10.18.0
node 24.21.0: installed
pnpm 10.18.0: installed
Managed tools use 218.9 MB in this clone's .turbo/tools.
Shared download cache: 62.3 MB.
Dependencies skipped (dependency installation is not supported yet). No tasks run.
```

Install dependencies the way your repository does today. `--tools-only` still works, and it also overrides `"dependencies": "locked"` for one invocation.

## `verify-system`

With `"tools": "verify-system"`, `turbo setup` records the versions of tools that are already installed in `turbo.lock` and verifies them on every run, instead of downloading them. Use it where managed tools aren't available, such as hosts without official Node.js builds like Alpine Linux, together with an exactly pinned image tag.

`verify-system` supports the `javascript` toolchain: Node.js and, if your repository declares it, pnpm.

```jsonc title="./turbo.json"
{
  "futureFlags": {
    "experimentalSetup": true,
  },
  "setup": {
    "dependencies": "skip",
    "javascript": { "tools": "verify-system" },
  },
}
```

<Callout type="warn">
  `verify-system` reduces the guarantee of managed tools. `turbo setup` checks
  the installed versions against `turbo.lock` but doesn't install them, so
  consistency depends on each machine.
</Callout>

### How it works

For each tool, `turbo setup` uses the first `node` or `pnpm` on `PATH` outside of your repository, so the repository can't supply its own executable. It runs `<tool> --version` from a temporary directory with Corepack downloads disabled and a 10-second timeout. It never downloads, installs, or writes to `.turbo/tools`.

| Mode                                   | Behavior                                                                                                                                                          |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Local                                  | Checks that the installed versions satisfy your declarations, records them in `turbo.lock` when the lock is missing or a declaration changed, then verifies them. |
| Frozen or CI, `--check`, and `--force` | Verifies without writing: `turbo.lock` matches your declarations, and each tool on `PATH` is exactly the locked version.                                          |
| `--update-lock`                        | Records the installed versions in `turbo.lock`, even for unchanged declarations.                                                                                  |

`--force` has nothing to reinstall, so it only verifies. Local mode still requires `/.turbo/` in your `.gitignore`, because `turbo setup` takes a lock under `.turbo/` while it writes `turbo.lock`.

```txt title="Terminal"
javascript: tools verify-system (turbo.json setup policy); dependencies skipped (turbo.json setup policy); turbo setup verifies the installed tools against turbo.lock but does not install them, so consistency depends on each machine
turbo.lock created. Commit turbo.lock to share the exact managed tool selections.
node: locked 24.17.0
pnpm: locked 10.28.0
node 24.17.0: verified at /usr/local/bin/node (verify-system)
pnpm 10.28.0: verified at /usr/local/bin/pnpm (verify-system)
Dependencies skipped. No tasks run; verify-system tools are not managed by turbo setup, so tasks use the verified tools on PATH.
```

`turbo.lock` records each tool's version and executable, without downloads:

```json title="./turbo.lock"
{
  "schemaVersion": 0,
  "tools": {
    "node": {
      "adapter": "node",
      "version": "24.17.0",
      "declarations": [{ "file": ".nvmrc", "request": "24" }],
      "installation": { "kind": "verify-system", "executables": ["node"] }
    }
  }
}
```

### Switching between `managed` and `verify-system`

A `turbo.lock` created under one mode isn't trusted under the other, so plain and frozen `turbo setup` fail after you change `tools`. Run `turbo setup --update-lock` locally and commit `turbo.lock`.

### Limitations

- Only Node.js and pnpm. A `packageManager` that pins npm, Yarn, or Bun isn't supported, and neither is a Corepack integrity suffix, such as `pnpm@10.28.0+sha512.<hex>`.
- npm isn't verified separately from Node.js.
- A repository can't mix managed and `verify-system` tools.
- `turbo setup --plan` isn't implemented for `verify-system` tools.
- `turbo run` and [`turbo exec`](/docs/reference/exec) fail in a repository whose `turbo.lock` records `verify-system` tools, even though `turbo setup` says tasks use the verified tools on `PATH`. On musl hosts, they also fail because managed runs aren't supported there. See [Managed toolchain platforms](/docs/reference/managed-toolchain-platforms#musl-linux).

```txt title="Terminal"
managed setup validation failed: turbo.lock selects verify-system tools, which come from PATH rather than a managed installation; run turbo setup --check to verify them
```

## Skipping toolchains

With `"tools": "skip"`, `turbo setup` neither installs nor verifies the toolchain, and tasks use whatever is on `PATH`. If every toolchain is skipped, `turbo setup` reports `Nothing to prepare` and exits successfully.

If you skip `javascript` while `turbo.lock` still records tools, `turbo setup` fails rather than ignoring the committed selections. Remove the skip, or remove the tools from `turbo.lock`.

<Callout type="info">
  When `experimentalCargoWorkspaces`, `experimentalPythonWorkspaces`, or
  `experimentalGoWorkspaces` is enabled, `turbo setup` considers that toolchain
  part of the repository and installs its [managed
  tools](/docs/reference/setup#other-toolchains). Rust, Python, and Go support
  `managed` and `skip`, not `verify-system`. Managed Rust, Python, or Go tools
  also need managed `javascript` tools when the repository has JavaScript
  declarations.
</Callout>

## Mirrors

`mirrors` sets where `turbo setup` downloads from. Each value is a base URL that serves the same paths as the official source it replaces:

| Key           | Replaces                                     | Downloads                                           |
| ------------- | -------------------------------------------- | --------------------------------------------------- |
| `node`        | `https://nodejs.org/dist`                    | Node.js release metadata and archives               |
| `npmRegistry` | `https://registry.npmjs.org`                 | npm, pnpm, and Yarn package metadata and tarballs   |
| `bun`         | `https://github.com`                         | Bun release checksums and archives                  |
| `uv`          | `https://releases.astral.sh`                 | uv's version index and release archives             |
| `python`      | `https://releases.astral.sh`                 | CPython build checksums and archives                |
| `go`          | `https://go.dev` and `https://dl.google.com` | Go's release index and archives                     |
| `rust`        | `https://static.rust-lang.org`               | rustup, Rust channel manifests, and Rust components |

`bun`, `uv`, `python`, `go`, and `rust` replace only the official host, so the mirror serves the official paths beneath its base. For example, with `"bun": "https://mirror.example.com/github"`, `turbo setup` downloads Bun 1.2.23's checksums from `https://mirror.example.com/github/oven-sh/bun/releases/download/bun-v1.2.23/SHASUMS256.txt`. Mirrors must serve these files themselves rather than redirect to another host.

Go publishes from two hosts, so one `go` mirror serves both of their paths. With `"go": "https://mirror.example.com/golang"`:

| Official URL                                           | Mirror URL                                                         |
| ------------------------------------------------------ | ------------------------------------------------------------------ |
| `https://go.dev/dl/?mode=json&include=all`             | `https://mirror.example.com/golang/dl/?mode=json&include=all`      |
| `https://dl.google.com/go/go1.24.2.linux-amd64.tar.gz` | `https://mirror.example.com/golang/go/go1.24.2.linux-amd64.tar.gz` |

Some public Go mirrors serve the release index but redirect archive downloads back to `dl.google.com`. They don't work as a `go` mirror.

`rust` works like rustup's `RUSTUP_DIST_SERVER`. `turbo setup` downloads rustup itself from the mirror and runs its private rustup with `RUSTUP_DIST_SERVER` set to the mirror and `RUSTUP_UPDATE_ROOT` set to its `/rustup` path, so Rust components download from the mirror too. Serve the official channel manifests unchanged. rustup checks each component against the channel manifest, and `turbo setup` checks that manifest's `.tar.gz` URLs and digests against `turbo.lock` before installing the toolchain.

<Callout type="warn">
  rustup downloads the `.tar.xz` copies of Rust components, and `turbo.lock`
  records only the `.tar.gz` digests. Through a `rust` mirror, those copies are
  verified against the channel manifest the mirror serves, not directly against
  `turbo.lock`. Use a Rust mirror you trust.
</Callout>

```jsonc title="./turbo.json"
{
  "futureFlags": {
    "experimentalSetup": true,
  },
  "setup": {
    "dependencies": "skip",
    "mirrors": {
      "node": "https://mirror.example.com/nodejs/dist",
      "npmRegistry": "https://mirror.example.com/npm",
    },
  },
}
```

- Each value must be an absolute `https://` URL without credentials, a query, or a fragment. `turbo.json` is committed, so it must never contain a secret. Errors name the key and mask the value.
- `turbo setup` sends no credentials to mirrors. Use a mirror that serves these downloads without authentication.
- `turbo.lock` keeps the official URLs, and every download is verified against the digest in `turbo.lock`, except Rust components, as described above. A lock created through a mirror that serves the official bytes is identical to one created without it, so other machines can use the official sources or another mirror.
- [Additional tools](/docs/reference/additional-tools) still download from their declared URLs.
- `--check`, `--offline`, and `turbo run` never download, so they never contact a mirror.

<Callout type="warn">
  When `turbo setup` creates or updates `turbo.lock` through a mirror, the
  digests it records are the ones the mirror served. Later setups verify those
  digests, but nothing checks them against the official source. Review
  `turbo.lock` changes made through a mirror as carefully as any other change.
</Callout>

`turbo setup` doesn't read npm configuration. A `registry` in `.npmrc` doesn't configure a mirror, and an `.npmrc` file still stops `turbo setup`, even when its registry matches `npmRegistry`. See [npm configuration](/docs/reference/setup#official-only-setup-rejects-npm-configuration).

### Environment overrides

`TURBO_SETUP_NODE_MIRROR`, `TURBO_SETUP_NPM_REGISTRY`, `TURBO_SETUP_BUN_MIRROR`, `TURBO_SETUP_UV_MIRROR`, `TURBO_SETUP_PYTHON_MIRROR`, `TURBO_SETUP_GO_MIRROR`, and `TURBO_SETUP_RUST_MIRROR` override `node`, `npmRegistry`, `bun`, `uv`, `python`, `go`, and `rust` for one invocation without changing `turbo.json`. They follow the same rules. For each mirror, `turbo setup` uses the first value it finds:

1. The environment variable. Empty variables are ignored.
2. The key in `setup.mirrors`.
3. The official source.

To use the official source despite a configured mirror, set the variable to the official URL:

```bash title="Terminal"
TURBO_SETUP_NODE_MIRROR=https://nodejs.org/dist turbo setup
```

## Troubleshooting

| Message                                                                                   | Fix                                                                                             |
| ----------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| `The "setup" key requires "futureFlags.experimentalSetup" to be enabled.`                 | Enable the flag in the root `turbo.json`, or remove `setup`.                                    |
| `The "setup" key can only be used in the root turbo.json.`                                | Move `setup` to the root `turbo.json`.                                                          |
| `The "<toolchain>" setup policy requires`                                                 | Enable the named workspace flag, or remove the toolchain key.                                   |
| `Setup dependencies cannot be "locked" when tools are "skip".`                            | Set `tools` to `managed` or `verify-system`, or set `dependencies` to `skip`.                   |
| `dependency setup requires a committed <lockfile>`                                        | Commit the lockfile, set `"dependencies": "skip"`, or pass `--tools-only`.                      |
| `verify-system tools for Rust, Python or Go workspaces`                                   | Set `tools` to `managed` or `skip` for Rust, Python, and Go.                                    |
| `managed Rust, Python or Go tools with a skip or verify-system JavaScript tools policy`   | Use `managed` `javascript` tools, or skip Rust, Python, and Go.                                 |
| `turbo.lock selects tools that the setup policy skips`                                    | Remove the skip, or remove the tools from `turbo.lock`.                                         |
| `official-only setup rejects ... configuration`                                           | An empty `"setup": {}` isn't accepted. Add a key or remove `setup`.                             |
| `setup.mirrors.<key> must be an absolute HTTPS URL`                                       | Use an `https://` base URL without credentials, a query, or a fragment.                         |
| `<tool> is not on PATH outside the repository`                                            | Install the tool, or use `managed` tools.                                                       |
| `<tool> at <path> is <version>, but turbo.lock requires <version>`                        | Install the locked version, or run `turbo setup --update-lock` locally and commit `turbo.lock`. |
| `installed <tool> <version> does not satisfy its native declaration`                      | Install a version that matches your declaration.                                                |
| `turbo.lock records <tool> as a managed tool, but the setup policy selects verify-system` | Run `turbo setup --update-lock` locally and commit `turbo.lock`.                                |
| `invalid locked Node artifact or mappings` after switching to `managed`                   | Run `turbo setup --update-lock` locally and commit `turbo.lock`.                                |
| `verify-system requires turbo.lock`                                                       | Run `turbo setup` locally and commit `turbo.lock`.                                              |
| `native declarations disagree with turbo.lock`                                            | Run `turbo setup` locally and commit `turbo.lock`.                                              |
| `verify-system supports Node.js and pnpm without Corepack integrity pins`                 | Declare pnpm without an integrity suffix, or use `managed` tools.                               |
