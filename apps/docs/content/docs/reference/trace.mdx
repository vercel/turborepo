`turbo trace` selects the test files that a change can affect. It follows the imports and other references of each test file through your repository, and reports a test when a changed file is in its trace.

```bash title="Terminal"
TURBO_EXPERIMENTAL_TRACE=1 turbo trace affected
```

<Callout type="warn" title="Experimental">
  `turbo trace` is experimental and hidden from `turbo --help`. Its flags,
  output and storage may change in any release.
</Callout>

<Callout type="info" title="Not the `--trace` flag">
  `turbo trace` is a command. The global `--trace <FILE>` flag is unrelated:
  it saves a performance trace of any `turbo` command to a file.
</Callout>

## Enabling the command

The command runs only when the [`TURBO_EXPERIMENTAL_TRACE`](/docs/reference/system-environment-variables#turbo_experimental_trace) environment variable is set to `1` or `true`. Without it, `turbo trace` means what it did before the command existed: `turbo run trace`, which runs a task named `trace`.

The variable is read only from the environment. It is not a `turbo.json` key, and it is not an input to task hashes: setting it does not change `turbo run`.

## Limitations

- **Not supported on Windows yet.** On Windows, the command exits with an error.
- **Flags only.** The command reads its options from flags. There is no configuration file, and `turbo trace lint` reads no baseline file.
- **The root `turbo.json`.** The trace reads `turbo.json` (or `turbo.jsonc`) at the repository root. With another one (`--root-turbo-json`), `turbo trace affected` selects every test, and `why` and `lint` stop with an error.
- **Static analysis.** Selection is a function of the base and head trees and the repository's configuration. It never runs your tests or your build.

## Storage and caching

The command stores the graph it builds in `.turbo/trace` at the root of the repository and refreshes it against the tree on each run. Like the rest of `.turbo`, it belongs in your `.gitignore`.

The graph's caches, some of which are keyed by this machine's file timestamps, are kept in your user cache directory (`~/.cache/turbo/trace` on Linux, `~/Library/Caches/turbo/trace` on macOS), never in `.turbo`. Restoring `.turbo` into another checkout, as `actions/cache` does, is safe: the graph is refreshed against that checkout's tree before it answers.

With [`cacheMaxAge`](/docs/reference/configuration#cachemaxage) or [`cacheMaxSize`](/docs/reference/configuration#cachemaxsize) set in `turbo.json`, the graph directory is cleaned up at the end of each command the way `.turbo/cache` is cleaned up for task outputs: the shards the current graph does not use are reclaimed first, then the age and size limits are applied to the graph's caches. The shards the graph needs are never evicted.

**Through Turborepo's cache.** In CI, `turbo trace affected` puts the graph it built into Turborepo's cache, under a key made of the commit SHA, the `turbo` version, the operating system and the architecture. A checkout without a graph fetches one before its first build: the graph of `HEAD`, else of the merge base with the base ref, else of one of the merge base's 20 nearest first-parent ancestors. The fetched graph is refreshed against the working tree, so it only saves time: the selection is the same as with a graph built from scratch. The graph goes wherever task outputs go: the local cache, [Remote Caching](/docs/core-concepts/remote-caching) (with signatures when enabled), `--cache-dir` and `--cache`. A machine outside CI fetches graphs and never puts one.

## `turbo trace affected`

List the test files that the changes between two git refs, or the given files, can affect.

```bash title="Terminal"
turbo trace affected [flags]
```

With no flags, the changes are those from the merge base with `main` to the working tree, including uncommitted and untracked files. The output lists one test path per line, relative to the repository root:

```txt title="Output"
packages/app/test/total.test.js
packages/math/test/add.test.js
```

<Callout type="warn">
  The comparison requires everything between base and head to exist in the
  checkout. If the changes cannot be read, every test is selected.
</Callout>

### `--base <ref>`

The base git ref for comparison. Defaults to the [`TURBO_SCM_BASE`](/docs/reference/system-environment-variables#turbo_scm_base) environment variable when it is set, else the merge base with `main`.

### `--head <ref>`

The head git ref for comparison. Defaults to the [`TURBO_SCM_HEAD`](/docs/reference/system-environment-variables#turbo_scm_head) environment variable when it is set, else the working tree.

The references between files are always read from the working tree. So when `--head` is not the checked-out commit (for example a commit ahead of `HEAD`), the files that differ between `--head` and the working tree count as changes too. The selection then covers more than the changes up to `--head`; check out `--head` first to select for exactly those.

### `--changed <file...>`

Use these files as the changes instead of reading them from git. Paths are relative to the current directory. A file that exists counts as modified; one that does not counts as deleted. Cannot be combined with `--base` or `--head`.

```bash title="Terminal"
turbo trace affected --changed packages/math/src/add.js
```

### `--filter <selector>` (`-F`)

Show only the tests of the packages that match the [filter](/docs/reference/run#--filter-string). The filter narrows the output only: selection always considers the whole repository, so a test in `app` that depends on a changed file in `math` is still reported with `--filter=app`.

### `--tests <framework...>`

Report only tests of these frameworks: `jest`, `vitest`, `gotest`, `cargo-test`, or `all`. Defaults to `all`. Any other value is an error.

### `--strict`

Make no assumptions: every uncertainty selects the tests it may affect.

### `--explain <test...>`

Explain why each of the given test files is or is not selected, instead of listing the selection. A file that the selection lists as an `UnknownTest` is explained as an unknown test, which always runs. Cannot be combined with `--json` or `--exit-code`.

The first line of each test says why it is selected. The indented lines below it list the uncertainties the test reaches and the assumptions made for it. With several tests, an uncertainty that an earlier test listed is not repeated. For the chain from the change to one test, link by link, use [`turbo trace why`](#turbo-trace-why-test-file).

### `--json`

Print the selection as JSON. Each list has the same shape as the `affectedTasks` field of [`turbo query affected`](/docs/reference/query#affected) (`items` and `length`), so the command can later move into `turbo query`:

```json title="Output"
{
  "affectedTests": {
    "items": [
      {
        "path": "packages/app/test/total.test.js",
        "package": "app",
        "task": "app#test",
        "reason": {
          "__typename": "FileChanged",
          "filePath": "packages/math/src/add.js"
        }
      }
    ],
    "length": 1
  },
  "uncoveredTasks": {
    "items": [],
    "length": 0
  }
}
```

Each item has:

- `path`: the test file, relative to the repository root.
- `package`: the name of the package that contains it (`//` for the root).
- `task`: the task that runs it (`<package>#<script>`), or `null` when none is known.
- `reason`: why it is selected. `__typename` is one of:

| `__typename`               | Meaning                                                                            | Fields        |
| -------------------------- | ---------------------------------------------------------------------------------- | ------------- |
| `TestChanged`              | The test file itself changed.                                                      |               |
| `FileChanged`              | A changed file is reached through imports.                                         | `filePath`    |
| `PackageDependencyChanged` | A third-party package that the test uses resolves differently.                    | `packageName` |
| `NameReferenced`           | A string in loaded code names a changed path.                                      | `filePath`    |
| `TaskChanged`              | A CI job, script or service that runs the test changed.                            | `filePath`    |
| `Uncertain`                | The test reaches code that cannot be analyzed statically, so any change selects it. | `filePath`    |
| `NotInGraph`               | A test file that is not a traced source file.                                      |               |
| `UnknownTest`              | A file that looks like a test in a package whose list of tests cannot be told (a runner's defaults, a pattern that leaves it out): always selected. |               |
| `AllTestsChanged`          | Every test is selected: the changes could not be read, or a file that steers the selection changed. | `description` |

`uncoveredTasks` lists the tasks that start tests the command cannot map to files, such as a runner it does not cover (mocha, `node --test`): each must run whole. Each has `task` (`<package>#<script>`), `package` and `description`. Without `--json`, they are printed to stderr.

With `--tests`, the tasks that start a framework you did not ask for are listed too, because the command selected none of their tests: for example, `--tests vitest` lists every task that runs jest. Run those tasks whole, or select their tests with another call (`--tests jest`).

The items are sorted by path, and two runs on the same tree print the same bytes.

### `--exit-code`

Exit with code `1` when a test is selected or a task must run whole, `0` when nothing must run, or `2` on errors. Useful for CI gating.

```bash title="Terminal"
turbo trace affected --exit-code
```

### `--cache-dir <path>`

The filesystem cache directory the graph is fetched from and, in CI, put into, as [`turbo run --cache-dir`](/docs/reference/run#--cache-dir-path).

### `--cache <options>`

Read and write the graph in the local and remote caches as [`turbo run --cache`](/docs/reference/run#--cache-options) does for task outputs. For example, `--cache=local:r,remote:r` fetches graphs but never puts one.

## `turbo trace why <test> [file]`

Explain why a change selects a test, in the terms of the selection itself: what changed, the code that makes the change matter (with its line of source), the kind of link, and each step from there to the test. Paths are relative to the current directory.

```bash title="Terminal"
turbo trace why packages/app/test/total.test.js packages/math/src/add.js
```

With a `file`, that file is the change. Without one, the changes are those of `turbo trace affected`, with the same `--base`, `--head` and `--changed` flags (and `--tests` and `--strict`):

```bash title="Terminal"
turbo trace why packages/app/test/total.test.js --base main
```

The command exits with code `0` when the change selects the test, and with `1` when it does not. Then it prints `not selected by this change`; with a `file` and the flags of a change, it also explains what else of that change selects the test.

The first line gives the reason as `turbo trace affected --json` reports it. Each numbered block below it is a witness: one way the change reaches the test.

```txt title="Output"
apps/web/test/cart.test.ts: selected by the change to packages/math/src/add.ts (modified) (FileChanged packages/math/src/add.ts)
  1. import: modified
        packages/math/src/add.ts
     -> packages/math/src/index.ts  (re_export "./add" at packages/math/src/index.ts:1)
     -> apps/web/test/cart.test.ts  (import "@acme/math" at apps/web/test/cart.test.ts:2)
  no other kind of link selects it (one witness per kind is known: the same kind may hold more constructs)
```

### Kinds of link

| Link                 | The change reaches the test because                                                                                      | Reason in `affected`  |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------ | --------------------- |
| `import`, `asset`    | A file imports or reads the changed file.                                                                                | `FileChanged`         |
| `the test itself`    | The test file changed.                                                                                                   | `TestChanged`         |
| `name reference`     | Code that is loaded together with a read of a computed path names the changed path: by a string or by a file's location. | `NameReferenced`      |
| `scope membership`   | The changed path matches the pattern that bounds a read.                                                                 | `FileChanged`         |
| `directory listing`  | The changed path was added to or removed from a directory that the code lists.                                           | `FileChanged`         |
| `task input`         | The changed file is an input of a task whose output the test loads.                                                      | `FileChanged`         |
| `task definition`    | A script, CI job or service that runs the test changed.                                                                  | `TaskChanged`         |
| `bounded load`       | A load with a computed target can reach a package that the change affects.                                               | `Uncertain`           |
| `open load or read`  | The test reaches code that cannot be analyzed. It is selected whatever changes.                                          | `Uncertain`           |
| `package dependency` | A third-party package resolves differently.                                                                              | `PackageDependencyChanged` |

A name reference shows the name and the read it is loaded with:

```txt title="Output"
services/billing/test/token.test.js: selected by the change to services/billing/secrets/dev.token (added) (NameReferenced services/billing/secrets/dev.token)
  1. name reference: changed services/billing/secrets/dev.token, named by the string 'secrets' in services/billing/test/paths.js:3 (loaded with the read at packages/reader/index.js:3, whose path is computed)
     services/billing/test/paths.js:3: return base + '/secrets/' + name + '.token';
     packages/reader/index.js:3: return fs.readFileSync(p, 'utf8');
        services/billing/test/paths.js
     -> services/billing/test/token.test.js  (require "./paths" at services/billing/test/token.test.js:2)
```

When the command knows what makes a construct broad, a `class` line says so. This name is the repository root, so every changed path matches it:

```txt title="Output"
apps/web/test/root.test.js: selected by the change to docs/guide.md (modified) (NameReferenced docs/guide.md)
  1. name reference: changed docs/guide.md, named by its own location (the repository root) in apps/web/test/root.test.js:4 (loaded with the read at packages/reader/index.js:3, whose path is computed)
     class: it names the repository root: every path of the repository is below it
     apps/web/test/root.test.js:4: const top = (name) => readText(path.join(ROOT, name));
     packages/reader/index.js:3: return fs.readFileSync(p, 'utf8');
        apps/web/test/root.test.js
```

The other classes are a read relative to the working directory, a listing or read below the repository root, a path chosen by an environment variable, and a load that only the declared packages bound.

A bounded load shows the load and the package it can reach:

```txt title="Output"
services/orders/test/routes.test.js: selected by the change to packages/util/other.js (modified) (Uncertain packages/framework/normalize.js)
  1. bounded load: uncertain (computed_specifier; the load can reach packages/util/ (packages/util/other.js changed))
     class: a load with a computed target, bounded only by the packages its package declares
     packages/framework/normalize.js:4: return [{ handler: () => import(spec), modulePath: spec }];
        packages/framework/normalize.js
     -> packages/harness/setup.js  (require "@acme/framework/normalize.js" at packages/harness/setup.js:1)
     -> services/orders/test/routes.test.js  (require "@acme/harness/setup.js" at services/orders/test/routes.test.js:1)
```

A load can also reach a package because a file of that package depends on the change, without being changed itself. The bound then names that file, and a `next:` line gives the command that explains it in turn:

```txt title="Output"
  1. bounded load: uncertain (computed_specifier; the load can reach packages/util/ (packages/util/list.js depends on the change))
     class: a load with a computed target, bounded only by the packages its package declares
     packages/framework/normalize.js:4: return [{ handler: () => import(spec), modulePath: spec }];
     next: turbo trace why packages/util/list.js  (why that file depends on the change)
```

A changed input of a task shows the task between the file and the test. Here the task also holds code that cannot be analyzed, which is a second witness:

```txt title="Output"
apps/web/lib.test.js: selected by the change to packages/lib/src/other.ts (modified) (FileChanged packages/lib/src/other.ts); it is selected with no change at all too
  selected through 2 independent witnesses: each selects the test by itself, so removing one does not unselect it. The first is the one `turbo trace affected` reports; also: task with an open uncertainty
  1. task input: modified
        packages/lib/src/other.ts
     -> members:packages/lib/src/**/*  (fs_read)
     -> task:packages/lib#build  (fs_read "members:packages/lib/src/**/* (tsconfig include)")
     -> apps/web/lib.test.js  (import "generated by task")
  2. task with an open uncertainty (needs no change): uncertain (computed_specifier)
     members:packages/lib/src/**/*: callers not known; parameter load#0; a value passed to packages/lib/src/index.ts:1
        members:packages/lib/src/**/*
     -> task:packages/lib#build  (fs_read "members:packages/lib/src/**/* (tsconfig include)")
     -> apps/web/lib.test.js  (import "generated by task")
```

### Several witnesses

A test is often selected in more than one way. Removing the construct of the first witness then changes nothing, because the next one still selects the test. `why` lists every witness it knows, as in the last example: each selects the test by itself. It knows one witness per kind of link, so the list is a lower bound: a kind may hold more constructs of the same sort.

### Selected with no change at all

A test that reaches code which cannot be analyzed is selected by every change, and also when nothing changed. So is a file that looks like a test and that no runner configuration lists (`UnknownTest`). `why` says `it is selected with no change at all too`, and marks the witness with `(needs no change)`.

### `--json`

Print the explanation as JSON. For a test: `test`, `selected`, `reason` (as in `turbo trace affected --json`), `noChange` and `witnesses`. Each witness has `reason`, `link`, `noChange`, `changed`, `description`, `class`, `code` (`file`, `line`, `text`), `chain` (`file`, `via`) and `next`.

## `turbo trace lint`

Report the code that cannot be analyzed statically, and the assumptions the selection makes. Exits with code `1` when there are findings, and `0` otherwise.

```bash title="Terminal"
turbo trace lint
```

### `--json`

Print the findings as JSON.
